§ 06

技術深水區

Technical Deep Dives

會議現場最容易被「技術試探」的八個題目。每題給出選型矩陣、踩坑清單、結論建議 — 對方丟出任何一題都能立刻接話、給出有層次的判斷。

01
離線 POS · Offline-First 架構
+

為什麼是紅線：餐廳尖峰時間網路斷線是常態（中華電信跳線、路由器死當、店面 4G 訊號弱）。POS 一旦不能開單，等於該店當機停業 — 客戶第一個 call 就是來罵這個。所以「斷網照常營業」是 POS 最重要的底線需求。

Architecture · 三層架構
Flutter UI → Local SQLite (write-first) → Outbox Queue → Laravel API

核心原則：本地永遠是真相來源（local-first），雲端是「最終一致」的副本。所有寫入先打到本地 SQLite，背景 worker 再非同步推送到後端；網路斷線時 worker 累積在 outbox，回線後一筆一筆補送。

Flutter 實作選型
套件 優點 缺點 選用建議
sqflite 最成熟、社群大 API 較原始、要自己寫 schema migration 小型 POS 可用
drift (前 moor) 型別安全、reactive stream、編譯期檢查 SQL 學習曲線稍高 推薦
Isar NoSQL、速度極快 原版已停更（v4 未正式釋出），新案請改用社群分叉 isar_plus 原版不建議；isar_plus 可考慮
Hive 輕量、純 Dart 無查詢能力；原版 3 年沒更新，社群分叉 hive_ce 較活躍 只能存 K/V 設定
衝突解決三大策略
LWW · Last Write Wins
  • 每筆紀錄帶 updated_at，新的覆蓋舊的
  • 簡單、適合單一裝置編輯的場景
  • 不適合店長和店員同時改同一張單
Append-Only Log
  • 所有寫入都是 event（加點、改桌、取消），不直接覆蓋
  • 用 event_sourcing 重建狀態
  • 推薦給 POS — 自帶 audit trail
Version Vector
  • 每筆紀錄帶 version + device_id
  • 能偵測「同時編輯」，丟回 UI 讓人決定
  • 實作複雜，過度設計
Edge Cases · 必須回答的細節
  • 收據號 / 發票字軌：離線時不能跟雲端要新字軌 → 改用「裝置預配字軌池」（每裝置預發 500 號），回線後申報
  • 信用卡刷卡：離線根本沒辦法授權 → 走「離線授權上限」（小額 500 元內），或直接降級成現金
  • 庫存扣減：離線可能超賣 → 採「樂觀扣減 + 回線重算」，並在 UI 標示「待同步」
  • 多裝置同店：店裡兩台 iPad 同時離線 → 用一台當 master 走區網（mDNS 廣播），所有人寫到 master 再同步雲端
常見地雷：把「同步」當成「複製」。同步必須處理刪除（tombstone）、改名、合併、衝突 — 不是 cron 跑 INSERT INTO 那麼簡單。第一版做錯，第二版基本上要重來。
初版規格只保證「離線寫入 + 回線追單」，不承諾「離線改單 / 離線退款」。寫成 SOW 紅字。Flutter 端用 drift，後端 outbox 用 Laravel queue + idempotency key 防重送。
02
多店資料隔離 · Multi-Tenancy
+

三種主流架構，沒有單一最佳解。要看「同集團多店」還是「不同集團獨立帳號」。肚肚客戶從單店到大型連鎖集團都有（其股東王品集團即為百店規模），很可能要混用。

選型矩陣
方案 隔離度 成本 備份/還原 跨店查詢 適用
Single DB
store_id column		 低 低 整個 DB 一起備份 容易（直接 JOIN） 單一集團多店 / 連鎖總部
Schema per Tenant
(PostgreSQL schema)		 中 中 單一 schema 還原 需 UNION 或 view SaaS 多客戶但同一資料庫實例
Database per Tenant 高 高 獨立還原最乾淨 困難（須跨 DB query） 金融級客戶 / 法規隔離
Laravel 套件
  • stancl/tenancy — 功能完整，支援 single DB / multi DB 切換，最主流（4.3k★ · 仍積極維護）
  • spatie/laravel-multitenancy — Spatie 出品，輕量、自己組裝（1.3k★）
  • archtechx/tenancy — 跟 stancl/tenancy 是同一個套件（作者 Samuel Štancl 把 GitHub org 從 stancl 搬到 archtechx，Composer 名仍為 stancl/tenancy）
必須一開始就決定的事
  • 每張表都要有 store_id + global scope，避免「忘了帶 store_id 害 A 店看到 B 店資料」這種致命 bug
  • queue job 要序列化 tenant context，否則背景任務會用錯店的設定
  • cache key 要帶 tenant prefix（Redis 共用時最容易出包）
  • File storage 要分租戶 disk（避免 A 店的圖片網址被 B 店看到）
常見地雷：用 middleware 在 request 開頭設 tenant，就以為全程都對。實際上 queue job、scheduled task、broadcast event 都跑在「沒有 request」的環境裡 — 必須單獨處理 context 傳遞。
給肚肚的建議：Single DB + store_id + global scope（用 stancl/tenancy 的 single-database mode）。理由：跨店報表是核心需求（連鎖看總部數據），DB-per-tenant 會讓 BI 很痛。等他們真的有「法規要求獨立部署」的客戶再切到 multi-DB。
03
即時訂單推播 · Realtime Architecture
+

POS 收單 → 廚房螢幕（KDS）3 秒內亮燈、店長 App 同時跳通知 — 這條鏈是「所見即所付」客戶體驗的關鍵。延遲超過 5 秒就會被罵。

四大方案比較
方案 適用場景 成本 自建難度 主要缺點
Laravel Reverb 同店端 KDS、店長 App 免費（自架） 低 連線數上限要自己壓測
Pusher / Ably 同上 + 不想顧 ops 按連線 / 訊息計費，量大很貴 零 每月帳單會嚇人
Firebase FCM 跨網路推播（店長離店時收通知） 免費（合理用量內） 低 非即時、最多 4KB、不保證送達
MQTT (EMQX / Mosquitto) IoT 級裝置、kiosk、KDS 大量並發 自架 EMQX 中 高（要懂 broker、topic 設計） 學習門檻高、Laravel 整合要自己寫
混搭策略（推薦給肚肚）
店內裝置 (WebSocket) + 店長離店 (FCM Push)
  • 店內：Laravel Reverb（自架）打開 WebSocket，給 KDS、結帳螢幕、桌邊 iPad 用。延遲 < 200ms。
  • 離店：FCM Push 同時發給店長 App。延遲幾秒可接受。
  • 不要用 Pusher：百店連鎖一天幾十萬訊息會吃掉 Pusher 的計費上限。
  • 不要選 MQTT：除非他們已經有 IoT 工程師 + 既有 MQTT broker，否則只是徒增複雜度。
常見地雷：把「即時」當成「會自動可靠送達」。WebSocket 斷線後再連回來、客戶端錯過幾筆訊息怎麼辦？必須加「broadcast + 補抓 API」雙保險 — 連回來後主動打 API 撈最新 N 筆，不能只靠 push。
初版用 Laravel Reverb + Redis pub/sub，跨網路通知再加 FCM。要避免一上來就上 Pusher（綁雲端帳單）或 MQTT（過度設計）。如果未來連線數爆掉再評估換 Soketi（Pusher 協定的 self-host 版）。
04
電子發票串接 · 字軌、載具、作廢、折讓
+

台灣電子發票是「看似簡單、實際全是規矩」的代表。財政部規範 + 加值中心限制 + 連鎖店業務情境，三方交叉踩雷。不熟的人接這題會延宕 2～3 週。

六大關鍵概念
概念 說明
字軌 向國稅局申請後、透過財政部電子發票整合服務平台取得的「發票號碼段」（如 AB-12345678 起 5000 號）。配號分 「年配」（一次一整年）與 「期配」（每兩月一期，雙數月 20 號後可取下一期）兩種。用完就不能再開。
載具 把發票「電子化儲存」的識別。財政部官方分為兩大類：(A) 共通性載具（含手機條碼、自然人憑證）、(B) 會員載具（店家自有）。
捐贈碼 消費者把發票直接捐給社福團體（例：捐 25885 = 創世）。一旦捐贈，消費者不能再列印。
作廢 當天或當期內，原發票整張取消。限時：當期結束前（雙月底前）。超過要走折讓。
折讓單 退貨、改金額的補救機制。2025/1/1 新制：由賣方單方開立並依限上傳（B2C 2 日內、B2B 7 日內），不再強制紙本雙方蓋章；只需「雙方合意」並保存合意訊息 5 年。可全額或部分。
上傳期限 2025/1/1 新制：B2C「開立後翌日起算 2 日內」上傳財政部、B2B「翌日起算 7 日內」（舊制 B2C 為 48 小時、2025/1/1 改為 2 日）。延遲會被罰。
加值中心比較
服務商 優點 缺點
綠界 ECPay 文件最全、串接簡單、金流發票一條龍 UI 較舊
藍新 NewebPay UI 較好、報表完整 客服回應時間長
ezPay（藍新旗下） 主打中小商家、費率漂亮、含發票服務 不只發票（另含電子錢包、收款），非純發票服務
關貿 Trade-Van 大型企業 / ERP / POS 整合主力 串接複雜、自助文件少（注意：「GENS」為俗稱、官方未使用此名稱）
必須在 SOW 寫死的細節
  • 字軌池由誰管理？（建議：加值中心 API 自動配發，肚肚總部監控餘量）
  • 離線開立的發票，怎麼確保字軌不重？（裝置預配 + checkout 強制檢查）
  • 退款流程：當日作廢還是隔日折讓？（影響 UI 流程設計）
  • 列印格式：消費者要不要紙本？（環保意識：預設不印，掃條碼存載具）
  • 「中獎發票」客訴：客人來抱怨領不到獎金，誰負責查？（建議切清楚是加值中心責任）
常見地雷：把「開發票」跟「上傳發票」當同一件事。實際上開立成功只是寫入本地 DB，必須另開一條 cron / queue 去跟加值中心對接上傳。一旦上傳失敗沒重試，48 小時後就被罰錢 — 你看到帳單才知道。
直接走「加值中心轉手」（綠界 / 藍新），不要自串財政部 MIG 規範。讓加值中心吃掉所有規範變動的責任。Laravel 端就維護一個「invoice_dispatch_job + 重試 + 監控告警」即可，把開發成本壓到 1～2 週內完工。
05
金流整合測試 · 沙箱、退刷、對帳、補單
+

金流是「能不能上線」的關鍵 — 任何錯誤都對應到「錢的去向」，會被銀行、客戶、會計三方追到底。測試必須做到「沙箱通過 → 正式微量真錢測 → 才放量」三段式。

沙箱測試的真相
沙箱能驗的
  • 請求/回應格式正確
  • checksum / MAC 簽章演算法
  • 正常付款流程
  • 明確的失敗代碼
沙箱驗不到的
  • 銀行端真實連線中斷（沙箱通常無此干擾，但官方文件並未宣稱「沙箱比正式穩定」— 屬工程師個人觀察）
  • 3D 驗證的 OTP 真實流程
  • 退刷與原刷的時間差（沙箱通常無法測退刷；正式環境消費者帳單回沖約 14-21 個工作天，商家額度恢復約 5-9 工作天）
  • 對帳檔的真實格式（工程界普遍觀察沙箱版有時較簡，無官方文件背書）
  • 限額 / 詐騙偵測攔截
必測情境清單
  • 成功流程：建單 → 付款 → 回拋 → 寫入 → 開發票
  • 付款中斷：使用者輸入到一半關掉視窗 → 訂單狀態？多久後過期？
  • 網路超時：送出付款請求後 timeout，但對方其實扣款成功 → 補單機制
  • 金額對不上：前後端金額不一致時誰為準（必須以後端為準）
  • 重複扣款：使用者按兩次「確認付款」（idempotency key 防呆）
  • 部分退刷：三品項只退一個（金流商支援嗎？）
  • 跨日退刷：當日刷昨天的單（多數金流不能跨日，要轉折讓）
  • 對帳差異：系統 100 筆，銀行 99 筆 → 哪一筆消失？
補單機制（Reconciliation Worker）
每日抓銀行對帳檔 → 比對 orders 表 → 差異訂單 flag → 人工確認 / 自動回沖

金流不是「打 API 成功就完工」。必須有一個獨立的 reconciliation worker 每日對帳，把「銀行說扣了但我系統沒記到」「我系統說付了但銀行說沒有」這兩種狀況揪出來。否則一個月後會計部會發瘋。

常見地雷：用「金流商回拋（webhook）成功」當訂單完成的單一信號源。Webhook 可能丟、可能晚到、可能重送 — 必須有「主動查單 API」當第二保險，否則使用者付了錢系統沒記到，會被告到死。
報價時把「金流模組」獨立列項，並加註：需要客戶提供測試卡號 + 沙箱帳號 + 正式環境少量真錢測試預算（建議 5,000～10,000 元）。對帳模組要單獨估工時，至少 5 個工作天，跟主流程拆開報。
06
熱感印表機相容性 · ESC/POS 戰場
+

「印表機應該都通用 ESC/POS 吧？」錯。ESC/POS 是「方言」，每家品牌都各自延伸自己的指令集，中文編碼、切紙、開錢櫃指令都不一定通用。這題會吃掉預想兩倍以上的工時。

市面主流品牌
品牌 市占 特點 坑點
Epson TM 系列 最高（POS 業界標竿） 文件完整、Linux 驅動齊全 貴，正版 3 萬以上
Star Micronics 中（國際品牌） 有完整 SDK 中文支援要設定 codepage
中崎 Aclas 中（中華電信常用） 便宜、ESC/POS 相容 韌體版本差異大、開錢櫃指令不同
SEWOO / Bixolon 低 韓系藍牙印表機常見 藍牙連線不穩
WINPOS 低（國產） 便宜、台灣總代 切紙指令獨家、需特別處理
連線方式四選一
USB
  • 最穩、最快
  • iPad 不能直接接（要 USB-C hub 或網路橋接）
  • Android 平板用 OTG 支援
LAN (Ethernet)
  • 最推薦給連鎖店
  • 固定 IP、多裝置共印
  • 不受系統權限限制
Bluetooth
  • 方便、無線
  • 不穩 — 連線會斷、要重新配對
  • iOS 走 MFi+CoreBluetooth 通常較穩；Android 因 OEM 背景殺 App 反而較不穩（業界常見反向認知，須注意）
Serial (RS232)
  • 老設備
  • iOS：原生不支援，需 MFi 認證 cable（如 Redpark Lightning-Serial）+ 廠商 App
  • Android：USB-Serial adapter（CH340 / CP2102 / FTDI）原生可支援
  • 只剩傳統收銀機在用
Flutter 套件 + 中文編碼
  • esc_pos_printer + esc_pos_utils — 老牌組合，文件多。但原版已停更，新案請改用社群分叉 esc_pos_utils_plus（2024-09 仍有更新）
  • flutter_thermal_printer — 新一點，支援 BLE / USB / Network 多種連線
  • blue_thermal_printer — 只支援 Android 藍牙
  • 中文編碼坑：大部分台灣印表機預設 Big5（CP950），不是 UTF-8。要先送「切換 codepage」指令再傳資料。
  • 圖檔列印：logo 要轉成 1-bit 點陣圖 + 對齊到 8 像素倍數，否則歪斜。
常見地雷：在辦公室用 Epson 開發完，到現場才知道客戶用中崎 — 切紙指令不一樣、開錢櫃指令不一樣、中文亂碼。解法：寫一個 PrinterDriver 抽象層，每家品牌一個 driver class，能 fallback 到通用 ESC/POS。
報價時限定支援的印表機型號清單（白名單），超出清單就要追加費用。SOW 寫明：「本案支援 Epson TM-T82 / TM-m30、Aclas PP9X / PP9MX」之類具體型號（注意：台灣業界口語常把 Aclas 叫「中崎」，但嚴格說 Aclas 是台灣頂尖科技、與中國「中崎電子」不同公司），不要寫「相容 ESC/POS 印表機」這種無底洞。
07
iPad POS vs Android POS · 設備抉擇影響整個 UI
+

「他們目前的 POS 是 iPad 還是 Android？」這題決定我們報價時整個 Flutter UI 規格 — 不是小事，是決定性的設備問題。會議第一個就要釐清。

兩派優劣對比
iPad POS（如 Square、iCHEF、肚肚）
  • 觸控體驗最好、店員學習門檻低
  • 更新策略統一（App Store）
  • 硬體穩定、回收價高
  • 缺：外接設備受限（藍牙印表機常出問題、不能接 USB POS 周邊）
  • 缺：租金高，1 台 1.5～2 萬
  • 缺：iOS 背景執行嚴格，背景同步要走 silent push
Android POS（手持機 / 平板 / 一體機）
  • 便宜、市場多選擇（Sunmi、新大陸、PAX）
  • 許多機型內建熱感印表機、刷卡機（一機到位）
  • 背景執行寬鬆、容易做背景同步
  • 缺：螢幕觸控品質參差、UI 要做更多容錯
  • 缺：OEM Android 版本碎片化（5.1～13 都還有人在用）
  • 缺：MDM 管理較複雜（要選 Sunmi 自家 / Scalefusion / Hexnode）
Flutter 在兩平台的差異
項目 iPad Android POS
藍牙印表機 CoreBluetooth 限制多，常斷 穩定、套件選擇多
USB 周邊 幾乎不可能 OTG 直接接
背景同步 嚴格、要 push 喚醒 寬鬆、Service 跑到爽
螢幕鎖定 Guided Access 內建 要 MDM 配合
OS 更新風險 統一可控 廠商定製、難測
使用體驗 最佳 看機型
如果他們已有原生 Swift POS
  • 不要主動建議換 Flutter。原生 Swift 在 POS 的優勢是 Flutter 短期追不上的（CoreBluetooth、Metal、battery 管理）
  • 提議方向：「新功能 / 周邊 App 用 Flutter，主 POS 不動」。例：店長行動管理 App、KDS、員工排班 App
  • 如果非要改寫，估工時要 ×2.5 以上（POS 邊界 case 比一般 App 多 10 倍）
常見地雷：在開發機用 iPad Air 測試一切順利，到客戶店裡才發現他們用 iPad 5th Gen (2017) — 跑不動、藍牙協定老、CPU 撐不住即時聚合查詢。SOW 必須寫明最低支援機型 + iOS 版本。
會議第一輪就問：「店家現在用什麼設備？iPad 還是 Android？型號？」如果是 iPad → Flutter 可做但藍牙、印表機要小心；如果是 Android POS → Flutter 是最佳選擇。不要在沒看到實機之前估工時。
08
既有系統 API 介接 · REST / GraphQL / Webhook / 直連 DB
+

外包模組 90% 的工時花在「跟既有系統怎麼接」。對方手上 API 的成熟度決定我們報價的下限。沒有看到 API 文件之前不報價。

四種介接方式比較
方式 成熟度需求 適用 陷阱
REST API 對方要有完整文件 主流、最容易接 分頁規範不統一、錯誤碼亂寫、版本斷層
GraphQL 對方要會自架 schema 大量資料、欄位常變動 學習門檻、N+1 query 容易踩
Webhook 對方願意主動推 事件驅動（新訂單通知） 重送、漏送、亂序 — 必須有補抓 API
直連 DB 對方願意給 read replica 只讀報表、BI 耦合死、schema 一改就壞、寫入絕對不行
必問清單（會議現場）
  • 「有 API 文件嗎？」沒有 → 我們要先做「API 摸索」，工時要加
  • 「API 是 REST、GraphQL 還是 SOAP？」聽到 SOAP / XML 整個工時 ×1.5
  • 「有 sandbox 環境嗎？」沒有 → 開發中我們會打到正式環境（風險高）
  • 「API 版本怎麼管理？」沒有版控 → 對方某天升版 = 我們現場炸
  • 「Rate limit 多少？」沒概念 → 高峰時段我們會被擋
  • 「Webhook 重試機制？保證送達？」沒有 → 必須做補抓 API
  • 「SLA 多少？」99% 跟 99.99% 工時差非常多
資料同步方向
單向 (POS → 我方)
  • BI、報表、CRM
  • 最安全、最容易做
  • 對方系統不會被影響
單向 (我方 → POS)
  • 會員資料寫回、優惠券發送
  • 要對方 API 支援寫入
  • 權限、稽核要小心
雙向同步
  • 排班、庫存即時雙向
  • 最危險 — 衝突解決機制要設計
  • 工時 ×2 起跳
常見地雷：對方說「我們有 API」，實際給的是「PHP 內部函式」而不是 HTTP API。或者給的是 admin 後台的「查詢介面 URL」，不能用程式呼叫。會議要當場請對方秀一段 Postman 範例，避免回去後才發現是空頭支票。
在 SOW 寫死「介接方式 = REST API、由對方提供完整文件 + sandbox」。如果現場確認對方沒有 sandbox / API 不成熟，要報「API 補完階段」獨立工時，避免我們被推著去自己摸索對方系統。直連 DB 只接受「read replica + 唯讀」場景。

  • 不要承諾硬體驅動開發 — 除非你們有韌體 / 嵌入式經驗

  • 不要在沒看到 SOW 之前報價 — 餐飲業客製需求很細，沒寫清楚會無限延伸

§ 10

術語說明

Glossary

本報告涉及的縮寫與技術名詞速查。會議時對方若提到任一詞彙，可直接對照。

商業 / 合約

SaaS
軟體即服務。雲端訂閱制軟體，按月付費而非買斷。
BI
商業智慧。把資料庫的交易紀錄轉成老闆看得懂的圖表報表。
CRM
客戶關係管理。會員資料、消費紀錄、行銷溝通的中央系統。
RFM
會員分群三維度：最近一次消費、消費頻率、消費金額。
ERP
企業資源規劃。總公司的內部後台，管財會、庫存、人資（如鼎新、SAP）。
SOW
工作說明書。合約附件，寫清楚要做什麼、不做什麼、交付什麼。
NDA
保密協議。雙方先簽，才能交換內部技術或商業資訊。
SLA
服務水準協議。承諾系統可用率（例如 99.9%）。
SI
系統整合商。專做大型整合案的公司（如鼎新顧問商）。
iPaaS
整合平台即服務。當作各系統間的「萬用轉接器」。

技術概念

API
系統與系統之間的溝通介面。POS 要傳資料給排班系統，就透過 API。
REST API
用 HTTP 方法（GET / POST / PUT / DELETE）做 API 的主流規範。
GraphQL
讓前端「自己決定要拿什麼欄位」的 API 規範，由 Meta 推出。
Webhook
系統主動通知對方的機制。POS 收到訂單 → 自動推一筆通知給庫存系統。
OAuth2
標準的授權登入流程。例如「用 Google 帳號登入」就是 OAuth2。
Idempotency
同一筆請求重複送出，結果應該不變。防止使用者連點兩次重複扣款。
WebSocket
瀏覽器跟伺服器維持「長連線」，可雙向即時推訊息（聊天室、KDS）。
MQTT
IoT 領域常用的輕量訊息協定。耗電低、適合大量裝置。
PWA
用瀏覽器開的網頁，但可加到手機桌面，操作像 App 一樣。
SPA
單頁應用。網頁不重新整理就能切換內容（如 Gmail、Notion）。
SSR
伺服器端渲染。傳統做法，每次點連結都重新讀整頁。
OLAP
線上分析處理。專為「大量資料聚合查詢」優化的資料庫類型。
Multi-Tenancy
多租戶。一套系統服務多個獨立客戶 / 店家，資料互相隔離。
Offline-First
App 設計哲學：本地永遠是真相來源，雲端是同步副本。
Outbox Pattern
把「待傳送的訊息」存在本地佇列，背景慢慢推給雲端，避免丟資料。
LLM
大型語言模型。ChatGPT、Claude、Gemini 這類 AI。
RAG
讓 AI 回答前先去查內部資料庫，避免亂講。
CV
電腦視覺。讓電腦「看圖」辨識內容的技術。
ML
機器學習。AI 訓練模型的統稱。

餐飲場景

POS
餐廳收銀系統。負責點餐、結帳、列印發票、出單給廚房。
KDS
廚房顯示系統。把訂單顯示在廚房螢幕上，取代紙本出單。
Kiosk
自助點餐機。客人自己操作的大螢幕點餐機（麥當勞那種）。
BOM
物料清單。一杯珍奶用幾克茶葉、幾顆珍珠的成本拆解表。
ESC/POS
EPSON 制定的熱感印表機指令集。所有市售收據印表機名義上都支援，但各家方言差異大。
EDC
刷卡機規格。串卡機收單時要照銀行的 EDC 規範。
字軌
透過財政部電子發票平台配發的「發票號碼段」，分年配（整年）/ 期配（每兩月）兩種。
載具
把發票電子化儲存的識別碼（手機條碼、自然人憑證、會員載具）。
折讓單
退款的補救機制（當期超過作廢時限就要用折讓）。
退刷
信用卡退款。當日可整筆退、隔日要走銀行對帳流程。
對帳檔
銀行 / 金流商每日提供的當日交易明細，用來跟系統比對找出差異。
OTG
USB On-The-Go。Android 手機 / 平板透過小轉接頭就能接 USB 鍵盤、印表機。
MDM
行動裝置管理。連鎖店遠端管控所有 iPad / Android POS 的工具。
Codepage
編碼頁。熱感印表機要先告訴它「我要傳什麼編碼」，Big5 / UTF-8 / GB2312 都不同。
LINE OA
LINE 官方帳號。店家在 LINE 上的客服與行銷管道。
LINE SPOT
LINE 內建的地點服務頁面，可導流到店家。

工具 / 套件

Laravel
主流的 PHP 後端框架。本提案的後端骨幹。
Flutter
Google 的跨平台 App 框架。一份程式碼能跑 iOS / Android / Windows / Mac。
Filament
Laravel 的後台系統產生器，快速做出管理介面。
ClickHouse
專門處理大量分析查詢的資料庫，比傳統 MySQL 快幾十倍。
Redis
記憶體型快取資料庫，用於排程、佇列、即時計數。
Horizon
Laravel 的佇列管理工具。
Reverb / Pusher
即時通訊服務。讓網頁能「主動」收到伺服器新訊息（如 KDS 即時收單）。
FCM
Google 的手機推播服務。
pgvector / Pinecone
向量資料庫。AI 應用裡用來做「相似度搜尋」（RAG 的後端）。
Metabase / Superset
開源 BI 工具，可直接接資料庫產出儀表板。
